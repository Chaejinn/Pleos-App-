응. 지금 단계에서는 작업 순서를 반드시 정하는 게 좋아. 특히 3명이 각자 기능을 개발하는 프로젝트라면, 단순히 담당 기능만 배정하는 것으로는 부족해.

왜냐하면 지금 기능명세서의 기능들이 서로 의존하고 있기 때문이야.

예를 들어 채진이 F-01(위치 수신)을 완성하지 않아도 동현이 F-05(지역 방문 판정)를 개발할 수 있어야 하고, 현민이 지역 데이터를 정리하는 동안에도 뱃지 시스템 개발이 진행되어야 해.

핵심은 기능 간 의존성을 정리하고, 병렬 개발이 가능하도록 인터페이스를 먼저 합의하는 것이야.

데이터 모델과 인터페이스만 합의되면 테스트용 경로 데이터를 사용해서 고스트 알고리즘을 먼저 개발할 수 있어.

# 3. 개발 시작 전에 세 명이 합의할 것

이 부분이 가장 중요해.

코드를 작성하기 전에 최소한 아래 네 가지는 결정하자.

공통 데이터 모델

`Trip`, `TrackPoint`, `RegionBadge`, `GhostResult` 등 각 기능이 공유하는 데이터 구조를 확정해.

특히 위도·경도, 시각, 거리, 진행 방향의 단위를 통일해야 해.

기능 간 인터페이스

위치 데이터를 전달하는 방식, 지역 방문 판정 결과, 뱃지 획득 이벤트, 고스트 인식 결과의 형식을 정해.

채진과 동현이 서로의 내부 구현에 의존하지 않도록 만드는 거야.

코드 소유 범위

동현은 판정 엔진과 도메인 모델, 채진은 Android 화면·SDK 어댑터·Room 저장 구현을 맡는 방식이 좋아.

공통 파일을 동시에 수정하는 상황을 줄일 수 있어.

공통 시연 경로

현민이 서로 다른 지역을 방문하고 과거 경로와 겹치는 테스트 경로를 준비하면, 세 명이 동일한 데이터를 가지고 개발하고 검증할 수 있어.

예를 들어 개발 인터페이스는 이런 식으로 합의하면 돼.

```
interface RegionVisitDetector {
    fun process(location: ValidatedLocation): List<BadgeEvent>
}

interface GhostDetector {
    fun process(location: ValidatedLocation): GhostEvent?
}
```

이렇게 해두면 동현은 Pleos SDK가 준비되지 않아도 알고리즘을 작성할 수 있고, 채진은 실제 위치 수신을 연결하기 전까지 가상 위치 데이터로 화면을 구현할 수 있어.

# 6. 팀 작업에서 반드시 지킬 규칙

세 명이 동시에 개발하는 만큼 Git 작업 방식도 정하자.

나는 복잡한 Git Flow보다 간단한 GitHub Flow를 추천해.

| 브랜치                    | 용도                |
| ---------------------- | ----------------- |
| `main`                 | 통합 및 실행 가능한 안정 버전 |
| `feature/location`     | 채진의 위치 수신 작업      |
| `feature/region-badge` | 동현의 지역 뱃지 판정      |
| `feature/ghost`        | 동현의 고스트 인식        |
| `feature/assets`       | 현민의 데이터·에셋 통합     |

작업 단위로 브랜치를 생성하고 Pull Request로 합치는 방식이야.

특히 다음 원칙을 추천해.

첫째, 각자 코드를 작성하기 전에 공통 인터페이스를 합의한다. 인터페이스가 변경되면 영향을 받는 팀원에게 알리고 함께 수정해야 해.

둘째, 매일 최소 한 번 통합한다. 11월 14일에 처음 합쳐보면 예상하지 못한 오류를 해결할 시간이 부족해.

셋째, 실제 SDK 없이도 테스트할 수 있도록 만든다. GPS 콜백이 없을 때 가상 주행 좌표를 순서대로 입력할 수 있다면 개발 속도가 훨씬 빨라져.

넷째, `main`은 항상 실행 가능한 상태를 유지한다. 통합 오류가 생긴 상태로 다음 작업을 진행하지 않도록 하자.

## 결론

지금 필요한 건 기능명세서를 더 복잡하게 만드는 게 아니라, 세 명이 서로 기다리지 않고 개발할 수 있는 작업 순서를 확정하는 거야.

나는 개발을 시작하기 전에 딱 세 가지 산출물을 만들기를 추천해.

1. 공통 데이터 모델 및 인터페이스 명세: 팀원 간 데이터 전달 규칙
2. 기능 의존성 및 담당 작업표: 어떤 기능을 언제 통합할지
3. 공통 시연 시나리오: 동일한 테스트 경로와 예상 결과

특히 첫 번째가 중요해. 이걸 정하지 않으면 채진은 화면과 SDK를 개발하고 동현은 알고리즘을 개발한 뒤, 통합 단계에서 데이터 형식이 맞지 않아 다시 수정하는 상황이 생길 수 있어.

내 추천은 11월 11일에 공통 인터페이스부터 확정하고, 11월 12일부터 세 명이 병렬 개발하는 방식이야.
